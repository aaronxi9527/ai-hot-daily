AI 总览

今天没有哪条产品发布值得大书特书，但有一组数字值得停下来看：瑞士、意大利、加拿大三国的网络安全机构在一周内先后确认，AI agent 已经在真实攻击里跑完全程——瑞士说每一起已知案例都成功入侵（5 起确认、3 起涉关键基础设施、2 起得手），意大利说多个 agent 并行、几小时内攻陷大量系统、还会实时写恶意代码绕终端防御，加拿大说从选定目标到拿到云管理员不到 3 小时。德国 BSI 同一天补上一句：ARTEX、CAIRN、PentAGI 这类框架把攻击自动化了。四家机构的处方却极其朴素：24 小时内打补丁、上 MFA、最小权限、少暴露。能力在飞，处方没变，这就是今天最不舒服的地方。

产品侧只有两条够格，但都在改「判断发生在哪一步」。Wiz 的 ADR 把运行时告警的坐标系从进程换成函数——同样是 /usr/bin/id，能追到是哪个 HTTP 入口、经过 PyYAML 的 UnsafeConstructor 进来的，于是它从噪音变成高置信告警；同样是 find .git-credentials，能追到是 CI 审计脚本第 55 行，于是它从疑似窃密变成正常行为，同一套机制同时降误报和提召回，这在检测类产品里很少见。卡巴斯基把威胁情报的读者从人换成 agent：KIRA 一键把几百条 IOC 压成摘要，且每段摘要都标注来源数据集，再用 MCP 让客户的 SOC agent 直接调用。国内一条是天融信把七款产品打包成卫生健康行业的智能体安全方案，方案本身不是新版本，但里面三个口径值得抄：输出侧识别急救指征转人工、检索是否与管床权限对齐、日志必须带「人+智能体+任务」。

行业侧三件事拼成一条线。SAP 的 Project Granite 里，攻击者用偷来的工程师 GitHub 令牌改了源码，SAP 的处置是先停自动化交付、再换代码签名密钥——他们担心的不是数据被读，是被改过的代码带着有效签名发出去，而「改过的代码有没有进过构建」这个问题官方至今没答。1Password 与 Todoist 同周验证了同一个入口：员工身份就是新的边界；而 Todoist 那条里攻击者在任务和评论里搜别家 API key的动作，比任何 DLP 规则都更能说明凭证管理该往哪走。MCP 官方 servers 修了八个洞，最刺眼的是只读的 git_status 也能触发仓库配置里的程序执行——只读工具不等于安全工具，而且 npm 改成语义版本后，自动化升级会静默跳过。一句话收束：这一轮真正被考验的不是模型会不会被骗，而是「谁的身份在动、动之前有没有人看过、以及出事时能不能在三小时内把它停掉」。

WizADR · 应用层运行时检测 · 调用栈归因🔥🔥

把运行时告警的坐标系从「进程」换成「函数」：Wiz ADR 把应用调用栈接进 Runtime Sensor，同一套机制同时降误报和提召回

11 月 26 日，Wiz 发布 Wiz ADR（Application Detection and Response），直接做进既有的 Wiz Runtime Sensor，不额外装 agent、不改代码，官方口径是「available now」。它补的是运行时检测长期缺的那一层：基础设施级事件（子进程派生、外连、系统调用）一直能看见，但看不见是哪段代码、哪个函数、从哪个入口把它调起来的。

机制是重建应用调用栈：既在触发告警的进程内部还原，也跨父子进程派生链还原——所以当一个 Web 服务拉起一条 shell 命令时，分析员看到的是发起它的那个应用函数。沿途它会打上上下文标签，例如 Request Handler、Python Request Handler Descendant、Dynamic Code Execution、Unsafe Deserialization，把裸函数调用翻译成可读的安全信号；这些标签本身还能直接触发高保真检测，或抬高既有告警的严重级。

第一个例子是「把噪音变成高置信」：一个容器化 Python FastAPI 服务突然以 root 身份派生 /usr/bin/id。这个二进制在 Linux 工作负载里太常见，纯 OS 规则报它只会把 SOC 淹掉，所以早期后渗透侦察经常就这么过去了。ADR 把这条派生追到 import_spellbook 这个 HTTP 端点、再追进 PyYAML 的 UnsafeConstructor，附上 Request Handler 等标签，直接给 High；Wiz Blue Agent 结合进程血缘与云上风险判定为 Malicious，再由 Wiz Workflows 通知对应团队并触发遏制。

第二个例子是「把疑似攻击判成正常」：一个跑在 CI runner 上的容器化 Go 服务 repohygiene，在构建后审计里执行 find /data -name .git-credentials -type f，OS 规则会判成凭据收集。ADR 配合 Wiz Code 做 Threat to Code 关联，把 Go 调用栈 Scanner.findGitCredentials 追到具体仓库、scanner.go 第 55 行与 GitHub 上的代码属主，把开发者自己的注释摆进告警里；Blue Agent 判定 Not Malicious 并在消耗人力之前降级。

它给出的动机也是这一周的主线：AI 辅助攻击把「披露到利用」压得很短，攻击者常常比工程团队打补丁更快；而被投毒的依赖和被注入的 AI agent 可以完全跑在合法应用进程里，连 CVE 都没有。这种情况下，「这段行为是应用本来就要做的，还是有人正在利用它」这个问题，只能靠应用层上下文回答。

判断：这条的价值不在「多了一个检测器」，而在换了一套判断依据。检测类产品长期在「误报」和「漏报」之间二选一，ADR 的做法是同时改两头——因为知道 /usr/bin/id 是从哪个 HTTP 入口进来的，它敢报；因为知道 find .git-credentials 是 CI 脚本第 55 行，它敢不报。要提醒两点：示例只给了 Python 与 Go，官方未公布支持的语言/框架清单，也未给性能开销；此外这是厂商自述，没有独立复现，采购前应在自己的容器里用两个真实场景验一遍。

Kaspersky威胁情报 · KIRA 助手 · MCP 接口🔥

把威胁情报的读者从人换成 agent：TIP 上线 KIRA 一键摘要与 MCP 接入，每段摘要都标注来源数据集

11 月 26 日，卡巴斯基更新 Kaspersky Threat Intelligence Portal（TIP），两件事：AI 助手 KIRA（Kaspersky Investigation and Response Assistant） 正式接进门户，以及支持 MCP 协议让第三方或自建 AI 应用直接接入。

KIRA 做的事很具体：分析师在 Threat Lookup 里发一次查询，它把从各来源汇聚来的数百条 IOC、检测规则与长篇威胁报告一键压成简短摘要，并标出该先看哪一条。对每个信息块，卡巴斯基定义了它所依据的来源数据集——这一点是整条里最值得抄的设计，它让「AI 说了什么」和「依据是什么」在同一屏里可核对，而不是让分析师再去翻一遍原文。摘要与检索同样适用于通过 OSINT 搜出来的 IOC。

MCP 那半边的定位写得很清楚：不像传统 API，MCP 是为「AI 模型做灵活动态查询、按需取外部威胁数据」设计的。接上之后，企业自己的 SOC agent 可以把 TIP 当成一个可调用的工具，实时拿卡巴斯基的全球分析结果，用于自动化工作流。

商业化没有另开一套：新 AI 能力包含在标准 Threat Lookup 许可里（含标准查询配额），需要更多可单独扩容。产品负责人 Alexander Mazikin 的说法是，这些能力的主要价值是压缩「拿到信息」到「决定怎么响应」之间的时间，把人从手工整理里解放出来做更复杂的判断。

判断：这是「威胁情报从人读变成 agent 读」的一个具体落点，而且落得很务实——没有做花哨的问答，只做了两件 agent 时代真正需要的事：把输出压到可读长度，并把接口做成 MCP 而不是 SDK。国内 TI 厂商（微步、奇安信、绿盟）都在做类似的事，最终差别会落在两个细节上：摘要能不能点回原始证据（卡巴斯基用来源数据集标注解决了），以及配额怎么算（agent 调用频次远高于人，按人/按席位计费的模型在这里会立刻穿）。

天融信行业方案 · 智能体安全 · 医疗场景🔥🔥

把七款产品装进一套「体检—监护—随访」：天融信发卫生健康行业智能体安全方案，三条口径比能力清单更值得抄

11 月 27 日，天融信发布卫生健康行业智能体安全方案，借用医疗自己的说法把智能体安全拆成三段：上线前「体检」、运行中「监护」、长期「随访」，落到七款产品加两项服务，按需组合。需要先说明：这是一次行业方案级整合发布，没有统一的新版本号，底座产品此前均已存在，增量在组合方式与行业口径。

体检段的三个动作都给了可核对的规模：AI 安全评估系统依托 38 万余条内容合规题库与 2100 余条智能体漏洞库，覆盖内容、语料、Skills、MCP 等风险，在 CDSS 辅助诊断、病历生成智能体上线前做全量检测，对面向患者的导诊、体检报告解读做内容合规检测；AI 智能体安全评估服务按九大维度 39 项检查，重点排查提示词劫持、恶意 MCP 插件、未审计医学计算器等供应链风险；大模型安全评估服务从通用、模型、管理三个维度出准入结论，衔接医院联合评估与备案要求，并在模型或知识库变更后复评。

监护段是三条纵深：大模型安全网关当「AI 防火墙」，拦提示词注入与越狱（含外院 PDF、转诊邮件里的间接注入），识别病历等敏感数据并按级分流，敏感请求只走院内模型；大模型数据安全监测系统审计训练、微调、RAG 语料及 MCP/API 交互内容，并监测检索是否与管床权限对齐；API 安全审计系统发现影子 AI 与影子智能体，监测越权调阅他科病历这类异常调用。三者支持串接、旁路与 Agent 探针三种部署。

随访段解决的是「试点变规模化之后谁来看」：AI 安全管理系统对全院及医共体的智能体、模型、插件统一纳管，集中下发策略、分级熔断并可一键切回人工，支撑卫健委与区域平台统一规则、统一看日志、分级暂停；AI 网关系统集中接管多模型接口，按临床科室、科研团队设 Token 预算，带负载均衡与故障切换；天问安全智能体平台承担安全智能体的部署、运行、控制与优化，7×24 协同处置。接入方式是网关、代理与旁路审计，不改 HIS/EMR。

判断：方案本身不是新版本，但里面有三条口径值得直接抄进产品设计。第一，输出侧识别胸痛、卒中等急救指征并转人工——这等于承认在医疗场景里，模型输出不能只看「合规不合规」，要看「临床后果」，这是行业方案里少见的把风险落到结果上。第二，「检索是否与管床权限对齐」把 RAG 的权限问题从架构讨论变成一条可检测项，这一条在别的行业同样成立（谁有权看哪一科的数据，检索器必须知道）。第三，日志必须带「人+智能体+任务」三元标识，理由是医疗纠纷溯源——这其实应该是所有行业 agent 日志的最低字段要求，而不是医疗专属。天融信近期已连发金融、政务、教育、交通同类方案，说明打法是「一套底座 + 行业模板」，那么产品差异就不在能力清单，而在模板密度与行业语料的厚度。

公安部 / 公安信安标委强制性行业标准 · 生成式 AI 服务🔥🔥🔥

生成式 AI 服务第一次进强制性标准体系：GA 1277.19—2026 定档 12 月 1 日实施，同批还有 API 安全分析与防护有效性验证的技术要求

公安部 2026 年第 3 号公共安全行业标准公告发布，由公安部信息系统安全标准化技术委员会归口的 25 项标准正式发布，其中强制性 2 项、推荐性 23 项。分量最重的一条是 GA 1277.19—2026《互联网交互式服务安全管理要求 第19部分：生成式人工智能服务》：首次制定，强制性，2026 年 12 月 1 日实施。另一项强制标准是 GA 559—2026（上网服务营业场所信息安全管理系统功能要求），代替 2005 年的三项旧标。

这条的意义不在编号，在「放进了哪个筐」。GA 1277 系列原本管的是互联网交互式服务（论坛、即时通讯、直播一类），把第 19 部分留给生成式 AI，等于把大模型服务接进已有的备案—检查—处罚通道，而不是另起一套监管体系。对企业的含义很直接：距生效只剩三天，提供生成式 AI 交互服务的单位需要按现有检查逻辑自查功能与流程配置。

23 项推荐性标准统一在 2027 年 3 月 1 日实施，其中成体系的是 GA/T 2451.1~2451.7—2026 网络安全评价指标体系七部分：总体框架、基础面、安全面、威胁面、失陷面评价指标，以及量化评价方法与评价指数——这是第一次把「网络安全水平」拆成可量化打分的一张表。

同批还有一批产品级技术要求，直接对应招标参数：GA/T 2452 深度合成图像检测系统评估指南、GA/T 2453 物联网安全状态监测产品、GA/T 2454 网络安全防护有效性验证系统、GA/T 2455 API 安全分析产品、GA/T 2456 数据安全交换平台、GA/T 2457 云会议系统、GA/T 2458 全流量网络回溯分析产品、GA/T 2459 智能网联汽车网络安全检测工具、GA/T 2460 关键信息基础设施安全运维指南。

判断：对厂商而言，GA/T 2455 与 GA/T 2454 是这批里最该先读的两份——API 安全分析与防护有效性验证恰好是这两年 AI 安全项目里最容易被质疑「你到底证明了什么」的两个品类，有了国标口径，投标时的能力描述会从形容词变成条款。对甲方而言，12 月 1 日生效的 GA 1277.19 与 2027 年 3 月生效的 2451 指标体系会形成两段节奏：先合规自查，再量化评价。建议现在就把「生成式 AI 服务的输入输出管理、内容标识、日志留存」三项对着标准过一遍，这三项在任何一次检查里都会被问到。

瑞士 NCSC / 意大利 ACN / 加拿大 CCCS / 德国 BSI监管通告 · 自主 agent 实战🔥🔥🔥

四国机构一周内说同一件事，但措辞的差异才是情报：瑞士说「每一起都得手」，加拿大说「还不是完全自主」，意大利说「agent 实时写恶意代码绕终端」

11 月 21 日至 26 日，加拿大、意大利、瑞士三国网络安全机构先后发出通告，德国 BSI 在 26 日补上一份，主题相同：攻击者正在用自主 AI agent 自动化攻击互联网暴露系统，包括关键基础设施。

瑞士 NCSC（11 月 24 日）称收到首批由 AI agent 协助实施的攻击报告，至少两个行业受影响、含关键基础设施运营者，每一起已知案例中 agent 都导致了成功入侵；并称互联网上可访问的进攻型 AI agent（如 ARTEX、CyberStrikeAI）自 10 月以来几乎翻倍。11 月 27 日，BACS 局长 Florian Schütz 对瑞士电台补充了数量：5 起确认案例，3 起涉及关键基础设施，2 起攻击得手。

意大利 CSIRT Italia 的描述最技术：检测到由自主 agent 驱动的大规模入侵活动，多个 agent 并行、数小时内攻陷大量系统；在已分析的活动中，agent 实时编写恶意代码以规避终端防御。它点名四类框架：ARTEX、CyberStrikeAI、DeepSeek Harness（Red Team 模式）、PentAGI。ACN 局长 Andrea Quacivi 的说法是「数字技术差距已不可持续」。

加拿大 CCCS（11 月 21 日）给的是分布数据：全球观测到的进攻型 AI 工具基础设施中约 46% 关联 ARTEX、28% CyberStrikeAI、14% PentAGI；ARTEX 开发者虽在 10 月 8 日限制了访问，但该工具已被复制超过 12,000 次；攻击尚非完全自主（人选定目标与目的），但中间环节已由机器完成，侦察与利用从数天/数周压缩到数分钟，某些活动中从选定目标到拿到云环境特权访问不到 3 小时；来自 ARTEX 服务器的对加活动已持续数月。德国 BSI（11 月 26 日）的通告标题就是结论：进攻性 agentic AI 正在加剧威胁态势，点名 ARTEX、CAIRN、PentAGI。

四家的处方几乎一致且朴素：减少互联网暴露面、关键补丁 24 小时内打、上 MFA 或 passkey、最小权限、隔离未打补丁的系统、盯云身份与 API 调用速率、抑制生产环境详细错误信息、限制生产服务器出站。

MCP 官方 servers工具供应链 · 八个漏洞 · 版本陷阱🔥🔥

MCP 参考服务器修八个洞：只读的 git_status 也能触发仓库配置里的程序执行，而且 npm 改了语义版本、自动化升级会静默跳过

11 月 27 日，Model Context Protocol 官方参考服务器发布 v2.6.0，修复 8 个漏洞，并补齐 v2.5.0 遗留的 2 项。受影响组件与目标版本：mcp-server-git、mcp-server-fetch → 2026.11.27，server-memory → 2.2.2，Windows 上的 server-filesystem → 2.4.1。

最重的一组在 git server。Git LFS 会从仓库自己的 .git/config 读取 lfs.extension、lfs.customtransfer、lfs.standalonetransferagent 等指向可执行程序的键并在服务进程权限下执行它们；官方 Docker 镜像又是系统级安装 LFS，于是六个工具（包括只读的 git_status、git_diff、git_add、git_checkout、git_merge）都能被一个恶意仓库触发执行。修复方式是清空仓库级的这些键，并设 GIT_LFS_SKIP_SMUDGE=1 关掉 LFS 下载。

其余 git 修复分三类。边界绕过：--repository 指定的根目录若其 .git 指针指向别处，会被当成本仓库，于是 git_show 能读到别的仓库内容——现在启动时记录根的 Git 目录，只接受自身的 linked worktree 与子模块；objects/info/alternates 存在 TOCTOU（检查时为空、Git 查询前被改写），改为每次调用建私有对象目录、只链本仓库对象；git_checkout/git_merge 写工作树后重新做一次边界检查（补齐 v2.5.0）。凭据泄露：remote 名里带制表符会让 URL 列错位、非 URL 起始值跳过脱敏，配合 url..insteadOf 可返回带凭据的 URL——改为与 git remote 自身列表比对。环境变量读取：repo_path 会被 GitPython 展开 $NAME/${NAME}，而「路径不存在」的报错会回显展开后的值，等于一次工具调用就能读服务进程的任意环境变量；现在不做任何变量展开。另外 git_merge 不再覆盖 .env 这类被忽略的本地文件。

另外两个组件：server-memory 2.2.2 修 saveGraph 在符号链接替换临时文件时改到 memory 路径之外文件权限的问题；mcp-server-fetch 把 robots.txt 规则补齐到反斜杠与路径参数写法；server-filesystem 2.4.1 在 Windows 上读前读后各查一次、拒绝含 junction/symlink 的路径——但「读期间换掉目录再换回」这类竞态仍检测不到。

还有一个容易被漏掉的坑：TypeScript 包从日期版本改成语义版本后，2.2.2 与 2.4.1 排序低于旧的日期版本，包管理器不会把它们当升级推给用户，必须显式安装。

判断：这批洞的共同点是「仓库自己的配置就是攻击面」。Git 的配置文件本来就能指定要启动哪些程序，每一个尊重该配置的 Git 特性都是一条路，维护者只能一个特性一个特性地堵——这也解释了为什么 v2.5.0 刚修完、v2.6.0 又补两个。给企业两条可执行结论：①升级必须显式指定版本，靠自动化的依赖升级流水线会静默跳过；②只读工具不等于安全工具，git_status 同样会触发执行。第三点更结构性：只要 agent 会 clone 或读一个不受信任的仓库，就必须假设那个仓库的配置文件是攻击载荷的一部分。

牛津大学等（arXiv）研究 · 监控器评估 · 假阴性率🔥🔥

同一个监控器，假阴性率能从 0.5% 摆到 20.8%：换个攻击生成方法，评估结论就变了

11 月 25 日提交的论文《Attack Policy Selection can Mislead Monitor Evaluators》做了一个很具体的事：拿一个已下线的 OpenAI 生产监控器当案例，测它的假阴性率（漏检率）对「用什么方法生成攻击策略」以及「该方法优化到什么程度」有多敏感。作者来自牛津等机构（含 Yarin Gal、Xander Davies）。

结果是一个区间而不是一个数字：在单一方法（强化学习）的不同优化档位之间，假阴性率从 0.5% 到 20.8%；在不同方法各自的最佳档位之间，从 6.4% 到 23.0%（优化提示 vs 改写转录）。所有攻击策略都只针对代理监控器开发，结果显示都能迁移到留出的 GPT-5.4 目标监控器。

论文指出的机制也值得记：攻击策略产出的转录只是「危险行为的代理」，这些代理会带入可见的痕迹——例如监控器看到的任务说明里并没有某个子任务，但转录里出现了围绕这个「side task」的推理——从而影响监控判断。因此换一个代理，就可能换掉整个评估的结论；要把某个结果当成部署性能的证据，需要额外论证这个代理为什么有信息量、保守性在哪里，而论文坦言「做出有说服力的论证仍是开放问题」。

判断：这条对买「监控类」产品的人最有用，因为它说明「我们拦截率 95%」这种话在方法学上几乎无意义——换一种攻击生成方式，同一个监控器就能从 0.5% 掉到 20.8%。可执行的动作有两条：①验收时要求厂商给出「攻击生成方法 × 优化档位」的完整矩阵，而不是一个最佳成绩；②矩阵里必须包含至少一个自适应红队（针对这套防御优化过的攻击），因为固定攻击集上的好成绩最容易骗人。这与本周另一条呼应：模型自我报告的置信度「校准看起来很好，但缺阈值分辨率」——同理，监控器在固定测试集上的表现，缺的是「面对会调整的攻击者」的分辨率。

AI 代码审查没有「强门槛」：三档投入下每一档都至少放行 45% 的「看起来对、实际错」补丁

11 月 25 日提交的论文《How Much Effort Does an AI Code Reviewer Need?》问了一个很实用的问题：当 AI 编码 agent 写代码的速度超过人能审的速度、团队开始加 AI 审查员时，审查员需要多大投入才够。方法是让 Claude Opus 5.5（预注册）、Sonnet 5.5 与 Haiku 5.5（探索性）在低、中、高三档 effort 下，审查同一批 90 个由 agent 写出的 Django 补丁（来自 SWE-bench Verified），再用加强后的 SWE-ABS 测试判定真伪：55 个错、35 个对。

结论一，投入确实有用：每一档模型里，高 effort 比低 effort 接受的错补丁更少——Opus 0.45 对 0.67，Sonnet 0.49 对 0.65，Haiku 0.51 对 0.78（Opus 与 Haiku 的差异统计显著）。

结论二，但「中档」很划算：Opus 的中档在高档 15 个百分点内非劣（差 0.018，95% CI [-0.065, 0.108]），而成本低 20%（未达到预注册的 30% 门槛）；Sonnet 与 Haiku 的中档分别便宜 39% 与 51%，但非劣性未成立。Haiku 高档的单次审查成本约为 Opus 中档的 8%，准确率差异未能定论。

最该被引用的是那句结论：没有任何一档是强门槛——每一档都至少接受了 45% 的错误补丁。作者还做了探索性分析：55 个错补丁里有 32 个「问题可能不需要失败测试所检查的东西」，把这 32 个剔除后，所有关于准确率的假设都不再成立。也就是说，这批补丁里相当一部分的「错」本身就有争议。

判断：这条给「用 AI 审查 AI 代码」的热潮浇了一盆准确的水，而且浇的位置很对——不是「AI 审查没用」，而是「它不能当闸门，只能当筛子」。两条可执行结论：①合入仍必须有人签，AI 审查的产出应该被定位成「提高人审的命中率」而不是「替代人审」；②验收时别只测「能不能找出已知漏洞」，要专门测「面对看起来合理、实际错误的补丁会不会放行」——后者才是生产里的主要失败模式，也是这篇论文唯一量化了的东西。另外提醒：这是预印本、单一 benchmark、单一语言栈（Django），不要把它当成跨语言的普适结论。

🧭趋势判断

四条，都是给动作的，不是给观点的。

「AI 辅助」正在从形容词变成时间刻度，防守方唯一能改的参数是「从告警到隔离」的分钟数

三国通告给出的数字是「选定目标到拿到云特权访问不到 3 小时」「侦察利用从数天变数分钟」；SAP 的处置是先停自动化交付、再换签名密钥。这些都不是「更强的攻击」，而是「更短的窗口」。可执行的动作顺序因此要改：先做能在分钟级切断的动作（撤 token、隔离身份、关流水线），再去做需要小时级的取证与修补。

员工的代码托管与 CI 身份，已经比边界设备更短的木板

SAP、1Password、Todoist 一周内三起，入口都是员工 GitHub 账号或被盗的 runner/CI 凭证；Wiz 还原的那起入侵里，攻击者专门翻员工 AI 编程助手的历史会话找生产 SSO 凭证。采购与运维的动作很具体：把「能访问仓库与 CI 的令牌」当成一级资产来盘点，给它们设过期时间，并把「AI 编码助手会话里出现过什么」纳入日志审查范围。

「下架工具」只能降低新增，不能降低存量威胁

ARTEX 已被复制超过 12,000 次、CyberStrikeAI 有数千个在用实例、Censys 还数到 1,400 多个默认口令的暴露控制台。所以「某框架被下架」不能作为风险下降的依据。可依赖的只有行为特征：凭证在非常用地或住宅代理 ASN 上使用、批量取密钥、创建挂载节点根文件系统的特权容器——这三条跨工具通用。

评估方法本身成了新的攻击面，验收矩阵比准确率数字更重要

监控器的假阴性率随攻击生成方法在 0.5%–20.8% 之间摆动；AI 代码审查每一档都至少放行 45% 的错补丁。两条合起来说明：今天多数「AI 判 AI」类产品的公开指标，测的是固定攻击集上的成绩。买这类产品时，要求厂商给出「方法 × 优化档位」的完整矩阵、并包含自适应红队，比看一个 95% 更有意义。
