Perplexity 开源 SPACE 智能体沙箱：9 款前沿模型 118 次逃逸尝试全部失败，CoreWeave / Akamai / Crusoe 已承接对外供给

SPACE 是 Perplexity 今年 7 月替换掉商用沙箱供应商后自研的智能体运行时，一直是 Computer（Portable Computer agents）的唯一底座，日均创建沙箱数百万次。
架构上有三个关键选择：① 每个沙箱跑在自带独立操作系统的轻量虚拟机里，与宿主形成硬隔离边界；② 把沙箱当作不可信环境，网络访问与平台凭证全部放在沙箱外部管理——智能体能连授权服务，但拿不到凭据本身；③ 对运行环境做文件快照与检查点，支持暂停/恢复/回滚/会话分支，且只存增量而非整份拷贝，官方称同等生产流量下沙箱创建速度比原供应商快 3 到 5 倍。
安全评估的口径要看清：Perplexity 让 9 款前沿模型主动尝试越狱，118 次尝试中无一实现从虚拟机逃逸到宿主，但有模型找到了绕过网络限制的方法；官方称已修复并在复测中未再成功，且用同一套测试跑了多家闭源商用沙箱，智能体可从其中多款成功逃逸。以上均为厂商自测，尚无第三方复现——这也正是开源的用意。
配套动作：代码已上 GitHub；CoreWeave、Akamai、Crusoe 三家已同意向客户提供 SPACE。与英伟达上月的 OpenShell 一起，开发者现在有两个可用的开源智能体沙箱底座。

SnykAppSec 智能体 · 依赖防火墙 · 密钥检测🔥🔥

Snyk 发布 Evo Agentic AppSec：一支安全智能体团队跑在既有确定性引擎上，并立下「生成者不能当验证者」的产品红线

产品拆成五个具名智能体，且可用状态差异很大，不能整体当作 GA：Evo Code Scanning Agent（前沿模型推理 + Snyk 静态分析，主打越权访问类问题）、Evo Dependency Firewall（安装时阻断恶意或越界包，明确点名 slopsquatting——攻击者抢注 AI 智能体幻觉出来的包名）、Evo Agentic Security Review（把整个仓库的安全评审交给智能体，自建应用模型与威胁模型）三者处于实验性预览；Evo Remediation Agent 为开放预览（先覆盖开源组件问题，可能破坏构建的修复只排队等审批、不自动合并）；Evo Secrets Detection、Evo ADS、Evo Continuous Offensive Security 为 GA。
设计原则值得单独记：CTO Manoj Nair 的表述是「生成者不能当验证者」——所有智能体都不给自己的活打分，修复是否成立由独立的持续攻击性安全（Evo Continuous Offensive Security）以对手视角打一遍来证明。权限边界也做了区分：编码智能体内做预防不需要人工签核（它本来就有写代码的授权），但修复触及可能已在运行的代码、且有别人对其负责，必须先赢得那个人信任。
厂商自述数据（非独立审计，需谨慎引用）：VulnBench 上「49.7% 的情况下 LLM 安全评审报出的问题在下一次运行中消失」；VulnBump 上纯 LLM 只产出 59.6% 可合并修复，Evo Remediation Agent 提升到 90%；客户侧严重/高危问题一年内增长 10 倍，产品数据约为每修复 1 个新增 8 个。

Safeguard运行时护栏 · 应用内中间件 · MCP 工具管控🔥🔥

Safeguard Guard 开放早期访问：把护栏做成一行中间件塞进应用内部，能看见「请求变成了什么 SQL、什么外呼、什么提示词」

核心差异点在检测位置。厂商的说法很直接：「应用前面的防火墙只能看见请求，看不见这个请求变成了哪条 SQL、哪次外呼、发给模型的哪段提示词」。Guard 跑在库与框架层，也就是输入真正被使用的地方，按「它将要做什么」而不是「它长什么样」来判断。
覆盖六类检查：SQL 注入（在查询时刻判断请求输入是否改变了查询结构，参数化查询永不触发）、命令注入/路径穿越/不安全反序列化、SSRF（按主机名实际解析出的 IP 判断，可阻断云元数据地址）、LLM 调用（提示词注入、提示词与输出中的密钥与个人数据、模型白名单、Token 与成本上限）、MCP 工具调用（按名称允许/拒绝/监控，并检查工具入参与返回）。
上线策略设计得比较克制，值得国内厂商对照：所有护栏默认 Monitor 模式（只记录「本会怎么做」而不改流量），转 Enforce 需要人做显式决定；无法判断时 fail-open 放行并记录事件；提供不改代码即可全关的 kill switch；每次决策只显示「哪个库调用、哪个请求字段触发」，不记录载荷值。接入形态为 Express / FastAPI / Django / Flask / Spring Boot / ASP.NET Core / Go 各一行中间件，另备零代码选项与 proxy/sidecar 模式。
分发方式刻意反常规：只走私有 registry.safeguard.sh 并需 pull token，不上公共包仓库，registry 也不把包名透传给公共源——直接封掉「仿冒同名包」这条供应链路径；每个版本签名并带 SBOM 与 SLSA 溯源。当前为早期访问，厂商自承尚未经客户验证。

nFOX Lab开源模型沙箱 · 内核级权限剥夺🔥

nFOX 开源 Blockhouse 沙箱：默认剥夺全部权限，靠 Linux 内核策略按需恢复，并给模型文件加 SHA-256 封印

出发点是一句设计哲学：「每个模型都可能是敌对的，我们就假定它敌对」。所以 Blockhouse 不靠「告诉模型不要做什么」，而是直接移除做这件事的能力——在应用层之下用 Linux 安全机制约束模型工作负载，默认零权限，由管理员通过策略显式恢复。
关键设计：所有通信经 Porthole 这条受监控通道，请求在放行前可被审查；运行时凭据与审计控制留在模型进程之外；文件访问与可外联目的地均为白名单；模型文件在提供前用 SHA-256 封印，一旦变动即停止服务；记录隔离事件，并在宿主机无法提供预期保护时告警。
支持 vLLM、SGLang、llama.cpp 三个推理引擎；配套 nFOX Platform 提供评测、部署与监控控制台（云虚机、租用 GPU 主机、本地 N 卡 Linux 服务器），上线前可检查模型配置、校验文件并用对抗性提示词试跑，生产负载走 OpenAI 兼容端点，运营证据可回流既有 EDR 与 SIEM，审计记录支持 JSON 与 Parquet。
许可与状态：Blockhouse 计划以 Apache 2.0 开源、面向合格企业做 beta 评测；平台侧按年收费。CEO Gordon Allott 明确说开源是为「让很多双眼睛来审」，并承认管理员仍可能误把一个恶意目的地加进白名单。

NVD 于 10 月 16 日 15:17:33Z 发布该记录（来源 cve@mitre.org，状态 Received，暂无 CVSS 评分、暂无受影响版本配置——编号已存在，分析尚未跟上）。研究者的实测对象是 ZCode 桌面客户端 3.11.2.6792（Windows x64），验证时间 9 月 8 日。类型为信任边界违规，影响为任意代码执行 + 信息泄露。
机制：ZCode 打开工作区时，会把仓库内的 .zcode/config.json 合并进自己的 mcp.servers 表，并立即连接其中声明的每个服务、不经任何用户批准；对 stdio 类型服务，客户端直接 spawn 配置里的命令。于是「打开一个仓库」等价于「执行该仓库声明的任意命令」。没有安全相关的点击、没有同意弹窗——复现日志显示打开文件夹后一秒内完成 MCP 握手并自动拉起 calc.exe，日志里有 8 个 EXECUTED 标记。

Safeguard 的说法最能概括这条趋势——「应用前面的防火墙只看得见请求，看不见这个请求变成了哪条 SQL、哪次外呼、发给模型的哪段提示词」。同一天里，Snyk 把修复动作拆给五个智能体并坚持「生成者不能当验证者」，Netskope 把 DLP 接进 LLM 响应做数据类型级拆解，Sophos 把 AI 发现下沉到终端上的本地模型与本地 MCP Server。外置网关负责收口，内置中间件负责看清细节，两条腿缺一不可。

3. MCP 的「配置入口」被证明是当前最脆弱的权限边界：一天三个 CVE，两个是同一类错

CVE-2026-88755（ZCode 打开工作区即自动连接仓库声明的 MCP Server，一秒内拉起 calc.exe，并顺带外泄 1,821 字节凭据文件）、CVE-2026-96620（Claude Agent SDK 的 resume 参数未校验，一个短横线开头的值就能注入 --mcp-config 在 SDK 权限控制之外执行命令）、CVE-2026-95182（DeepSeek Harness 把裸命令名按 PATH 解析，而 PATH 前两项恰是模型可写的 node_modules/.bin）。三条的共同点是：配置文件与命令行参数被当成「数据」，而它们实际上是「权限」。

4. AI 凭据已进入黑产定价体系，而「不偷源码」这条规律出现了例外

Symantec 报告 Aoki 把 .claude.json、Codex config.toml/.env、Copilot/Cursor/Gemini 令牌与 AWS 凭据加入目标清单，判断是「像卡数据一样可以直接变现（转卖或 LLMjacking 跑满用量），但比卡数据多给一条通往开发者环境的路径」。六天前的 Warden Stealer 刚把同类能力做成涨价功能——一周内两家厂商、两套代码库收敛到同一个目标，说明这是需求侧驱动而非单点演进。唯一例外是 Cursor 本地状态库缓存对话与代码片段，偷它等于偷代码库的一部分。

5. 治理的瓶颈被量化了：不是缺技术，是缺流程位置

IDC 阿联酋研究给出三个数字串成因果链——98% 的安全团队已在生产环境遇到 AI 风险、十分之一 认为自己对智能体部署「完全准备好」、仅 15% 的 CISO 对 AI 部署拥有强制审批权且 仅 10% 的组织在评估方案前先定义安全要求。Opsin 的客户数据是另一面镜子：93% 接入智能体的工具拥有完全不受限的访问权，200 个里只有 1 个在动作前需要人工批准。两句话合起来就是：安全没被放进决策链的前面，所以只能靠事后拦。

6. 国内从「发产品」转向「拿认证 + 接国家级信任锚点 + 谈订单」

同一天里，阿里云 ATS 把智能体身份接到 CNNIC 的 DNS + PKI 上（身份证书由 CNNIC 私有 CA 签发），华为 FusionSolar Agent 拿下信通院 AIIA/T 0293-2026 Claw 类智能体风险管理专项证书（新能源光储首个），天融信把八款产品打包成教育行业方案并援引网安标委教育指引，启云方这类非安全背景的工业软件商也带着「三层网关 + 六层围栏」入场。券商研报的定性是「从产品发布期进入订单验证期」——而出口管制新规则同时把大模型与智能体写进了禁限目录。「能卖」与「能出去」现在是两套并行的合规门槛。
