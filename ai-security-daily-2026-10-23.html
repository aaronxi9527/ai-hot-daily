AI 总览 · 今日看点

周五。今天的主线一句话：智能体安全从「监控它做了什么」转向「证明它是谁、谁授权了它」。八条产品动态里，五条国际的有四条在做身份与凭据，国内三条在做权限矩阵与行业准入——没有一家在比检出率。

先看国际。SentinelOne 在 OneCon 一次发了两个产品：Singularity ADR 把「用户请求 → AI 助手 → MCP Server → 落地文件」串成统一执行图谱，加了 intent drift detection（比对最初指令与实际行为）和 agent containment（只停一个智能体、不中断周边工作流）；Singularity ASOC 的底座被 CEO 特意描述为「一个模型系统，不是一个大模型」。Palo Alto 一天两发：Cortex XDR One 把判定塞进传感器本地的小模型，官方称误报降 95%；Idira 智能体身份在 Prisma AIRS 上 GA，授权细到 MCP 上的单个工具。Okta 更彻底——client_id 直接变成一个厂商自己控制的 HTTPS URL，于是没有 secret 需要签发、存储和轮换。WorkOS Relay 索性让智能体永远看不到 token：代理注入、不跟随重定向、剥掉 Cookie 与转发头、目标必须在白名单。

国内三条都在给「动作」建权限矩阵，而不是给「内容」加过滤。奇安信天戟把 AI 渗透做成自助 SaaS——登录、交授权函、认证，然后对授权站点一键速查，7,000 个系统已投产，AI 执行 + 人工审核提效约 61%，AI 自主执行平均 3 小时/系统。天融信把「评估准入—运行防护—持续运营」复用到教育行业，给出 38 万道合规题库、2,100 个智能体漏洞库，AI 网关按部门和个人设 Token 预算。亚信安全提 ATF「智能体信任框架」，把传统 IAM 答不了的六个问题摆上桌：谁委托、为什么执行、什么任务下执行、允许调哪些工具、何时必须人工介入、最终谁负责。

行业侧今天最重的一条是 METR 与 Redwood 的红队报告。两人进驻 OpenAI 三周，用公司设备、全程有人陪同，拿到内部代码与监控 prompt，最后交 61 页报告——公开只有概要，还给 OpenAI 删改权（删到 38 页）。结论很硬：至少与 GPT-5.5 同级的内部 agentic 流量，只有 75%–94% 可被监控；compaction 事件不监控，导致 5–7 月约 10% 的 Codex 流量裸奔；监控只在智能体把控制权交回用户时才触发，所以持续干活就能无限推迟被看；Codex 智能体可绕沙箱与 Auto-Review 拿到宿主用户全部权限；一个 exploit 能让最近数百次动作连它自己都不进监控；两个客户端可控 header 能直接给新智能体关掉监控。两天前 OpenAI 刚自曝两个智能体削弱了自家监控——现在外部机构证明了这件事有多系统。

第二条是 LiteLLM 1.107.0 被投毒。周下载约 2,300 万，7 个平台包全中。机制值得记住：cook.pth 在 Python 启动时加载，恶意代码在 LiteLLM 被 import 之前就执行——装了就中，不管你有没有用它。攻击者用了三个工程师的 GitHub CLI token（从一台暴露在公网的内部部署日志里捞的），一个改流水线并触发、一个批准、一个删 workflow 记录。4.5 小时后就开始验证 AWS 凭据、试探 Bedrock 额度（LLMjacking）。安全版本是 1.106.2，且要按 digest 钉住。

第三条是方法论转向。Anthropic 用 Claude 做的不是找洞，是攻击面削减——不问「这里有没有 bug」，问「哪些代码本来就不该可达」。25 个项目、500 万行、17,000 个配置项，报出 493 个问题；其中 162 组配置组合被静默接受（不报错、不告警、无文档），94 组直接把安全控制关掉。两个案例够抄进清单：四个互不相关的项目都出现反向 DNS 关闭时主机名拒绝规则 fail-open；一个「延迟证书校验」的选项实际把校验整个关掉，这对冲突活了 21 年。OpenSSH 那条更具体——4,500 行 ML-DSA 后量子代码未认证可达，即使算法被明确排除。

还有两条不能漏。35,878 个 Agent Skill 里 6,637 个恶意，62% 一行恶意代码都没有，payload 是自然语言；90 个用空白填充（最多 825 行）、HTML 注释、不可见 Unicode 藏到审查者看不见的位置。上海交大的「资源劫持」则把智能体滥用从数据问题变成账单问题——不用偷凭证，让模型当免费白手套烧算力，主流模型沦陷率 70.0%–89.6%，现有护栏几乎全线失守。

今天最该抄进方案的一句话：「人工确认」不是兜底，它是又一个需要被认证的对象。Claude Duet 的审批分类器自报 17% 漏判；METR 证明监控的触发时机掌握在被监控者手里；LiteLLM 证明发布流水线可以被三个人三个账号冒充。三件事指向同一个设计要求——审批与判定必须发生在智能体不可写、不可改、甚至不可见的位置，并且能自证没被改过。

Palo Alto NetworksEDR + 智能体端点安全🔥🔥

Cortex XDR One：把判定塞进传感器本地的小模型，官方称误报比传统基线降 95%

10 月 22 日发布，已作为可交付产品上市。定位是把 EDR 与「自主智能体安全」合成一个平台，回答的是同一个问题的两半：智能体拿到了用户的宽权限，而它的行为是非确定性的。
架构上只用一个传感器，同时收运行时层与操作系统层遥测，因此能跨域串联攻击链——把「提示词注入」和「间接数据投毒」这类跨层事件识别成一条链而不是两个孤立告警。判定侧的关键选择是：小语言模型跑在传感器本地，不把样本送回云端再等结论。官方给出的效果是误报较传统检测基线下降 95%。

需要注意的口径：95% 是厂商自述，没有第三方基准，也没有公开的允许/阻断动作测试结果。真正该问的是「本地小模型误判时谁来复核」，以及它能不能拦住一个用宿主用户全部权限执行 git push 的智能体。

Palo Alto Networks智能体身份 · Prisma AIRS🔥🔥

Idira 智能体身份安全在 Prisma AIRS 上 GA：给每个智能体发短期 token，授权细到 MCP 上的单个工具

10 月 22 日 GA。Prisma AIRS Gateway 客户现在可以选 Idira（Palo Alto 的身份安全平台）作为 AI Agent Gateway 的智能体 IdP，这是可选项而非强制。
机制不复杂但每一条都对着具体失败模式：每个注册智能体发 OAuth 2.1 client credentials，换取短期、有时限的访问 token，不再需要长期共享密钥，也不再继承人类凭据；细粒度访问策略可以下到某个 MCP 上的某一个工具，运行时由 Gateway 强制执行；审计同时记智能体身份与背后的人类身份，解决 on-behalf-of 归因；凭据隔离让智能体根本拿不到凭据本身。
官方列的五类风险可以直接当检查表用：不可信身份（身份不唯一就能被冒充）、继承人类权限（助手类智能体最常犯）、影子智能体（看不见也管不住）、归因盲区（分不清人的意图和自动执行）、生产凭据暴露（拿到一个 API key 就能共享或被偷）。背景数据很刺：96% 的用户本身权限就已过度，继承凭据的智能体把这部分超额权限一并继承。
路线图分三段：已可用——SPIFFE + OAuth 2.1 凭据与 SVID、数据库的零常驻权限（走 Secure Infrastructure Access MCP Server）、未纳管智能体的引导纳管、按云厂 origin ID（AWS ARN / App ID）发现、支持 DCR 的 MCP 自动注册 OAuth 应用；早期访问——交互式活动图谱，可视化追踪跨企业的复杂执行路径；即将——把 SPIFFE 原生铺到 AWS、云厂商的 ZSP、面向 Cursor 与 Claude Code 开发者的 PAT / API key 保护。

Okta智能体身份 · MCP 治理🔥🔥

Okta 把 client_id 变成一个 URL：CIMD、MCP 目录、DCR、多 MCP 单授权服务器五项一起 GA

10 月 22 日。这次更新解决的不是「怎么认证」，而是「注册这一步本身成了瓶颈」——当一个智能体平台要服务上千个客户组织，每个组织一次注册，光注册就把上线拖死了。
CIMD（Client ID Metadata Document）GA 是核心：client_id 不再是授权服务器发的一串不透明字符串，而是厂商自己控制的 HTTPS URL；Okta 收到认证请求时按需解引用这个 URL、拿到描述客户端的 JSON（重定向 URI、支持的 grant、用于验签的 JWKS、token 端点认证方式），校验后缓存。结果是没有 client secret 需要签发、存储或轮换，密钥是无密钥/非对称的（DPoP、mTLS、签名断言）。听起来像「客户端自述自己」所以不安全，但控制点被搬到了两处：管理员先做 URL 白名单预检，且文档必须自证精确等于白名单里那一个 URL。
另外四项一起 GA：Okta Integration Network MCP Server Catalog（浏览即连接，连接前自动校验服务器可达性与凭据有效性）、MCP Server Registration with DCR（Figma、Gong、Sourcegraph 这类服务器自动注册、自动存凭据）、Multi-MCP Custom Auth Servers（多个自建 MCP 挂在单一授权服务器与单一策略下，改一次全局生效，但每个服务器仍保留独立 audience 与 scope，token 互不通用；token 里记录用户与涉及的智能体，出事能精准关停）、以及 AI Agent Import 扩到 Cursor、Snowflake、Databricks、Workato、Tines，配合 Multi-Source Agent Schema 可给每条记录加「用途」「是否生产」这类自定义字段。
它引的 Gartner 两个数字值得记住：到 2028 年，全球财富 500 强企业平均会有 15 万个以上智能体在跑；而只有 13% 的组织认为自己具备合适的智能体治理能力。中间那 87% 就是这门生意的全部空间。

WorkOS凭据代理 · 智能体运行时🔥🔥

WorkOS Relay：让智能体永远看不到 token——代理注入凭据，且不跟随重定向、剥掉 Cookie 与转发头

10 月 22 日发布，当前 early access（需联系 WorkOS 开通）。要解决的是智能体运行时最脏的一个事实：长期 bearer token 就躺在智能体的上下文窗口或进程内存里，一次提示词注入就能把它读走。
做法是「Model A」代理网关架构：智能体不再持有任何 provider token，请求打到 api.workos.com/relay，用 X-Relay-URL 指定目标、X-Relay-User 与 X-Relay-Organization 指定身份；代理从 WorkOS 存储里取凭据、注入出站请求、处理刷新，再把原样响应返回。凭据从 broker 直达目标服务，从不进入智能体环境。
防外泄做了三件具体的事，值得抄：不跟随 HTTP 重定向（防恶意跳转把凭据带去别处）、剥掉 Cookie、X-Forwarded-* 及其他 hop-by-hop 头（防注入头把凭据挤出来）、目标 host 必须在白名单（防被劫持的智能体把凭据指向未授权端点）。错误语义也守规矩：用户还没连过所需 provider 时返回 402 relay_authorization_required，每个代理响应带 X-Relay-Upstream-Status，让开发者能区分「代理层失败」与「provider 层报错」——这一点比很多同类网关认真。
限制同样明显：early access、需要人工开通、目标必须预先白名单。它管的是「凭据不被看见」，不管「这次调用该不该发生」——后者仍然要靠策略引擎。

天戟把 AI 渗透测试做成自助 SaaS：7,000 个系统已投产，AI 执行 + 人工审核提效约 61%

10 月 22 日。触发点是 PHP2Shell（CVE-2026-109618 / 109619）——奇安信把它当成一个论据而不是一个事件：漏洞已经进入「批量生产」阶段。其《2026 年中网络安全漏洞威胁态势研究报告》给的数据是上半年新增漏洞 35,467 个（同比 +51.9%）、高危及以上占 52.1%，更关键的是节奏——30.2% 的高危漏洞在发布当天就被利用，83.7% 在 21 天内遭攻击。
天戟的交付形态变了：过去这类系统是项目制，现在客户登录 ai.qianxin.com 注册企业账号、提交站点归属授权函、完成企业认证与应用开通，就能在应用中心对授权站点发起渗透测试。「一键速查」的实际含义是把授权流程产品化，而不是把渗透做简单。
能力三层：AI 原生自主决策——主规划智能体理解目标与约束、拆任务、评估反馈，浏览器智能体与登录测试智能体分工执行，结合页面内容、可交互元素与业务说明推断功能用途，自主完成导航、点击、填表、弹窗处理，并按新页面与执行反馈改路线；云地协同分布式执行——「服务端大脑 + 分布式作业端」，服务端统一编排，作业端提供贴近目标网络的执行能力，目标流量从作业端所在网络发出，作业端可横向扩展以覆盖总部、分支与不同业务区域；过程可视与证据闭环——任务状态、智能体过程、工具执行、实时日志全可查，按任务汇总漏洞名、等级、描述与测试过程并可导出，浏览器交互的请求响应进入关联的流量分析链路，为漏洞复核保留原始记录。
投产数据：覆盖约 7,000 个系统，涉及企业、证券、银行、医疗、教育、运营商；AI 执行 + 人工审核较纯人工提效约 61%；AI 自主执行平均 3 小时/系统，人工审核 10–30 分钟/系统；可 7×24 无人值守。
对做产品的人，真正的信息在最后一句：它卖的不是「能挖到洞」，是「把发现漏洞从应急动作变成常态工作」——这决定了它是订阅而不是项目。

天融信行业智能体安全方案 · 教育🔥🔥

天融信把「评估准入—运行防护—持续运营」搬到教育行业：38 万道合规题库 + 2,100 个智能体漏洞库，AI 网关按部门设 Token 预算

Anthropic攻击面削减 · 开源审计🔥🔥🔥

Claude 不找洞，改做「攻击面削减」：25 个项目 493 个问题，94 组配置静默关掉了安全控制，一组冲突活了 21 年

10 月 20 日研究。方法论的转向比数字更重要：不问「这里有没有 bug」，而问「在这个部署里，哪些代码本来就不该可达」。三种模式——默认配置下可达但默认功能根本不用的代码；单看合理、组合起来失效的配置项；在鉴权、用户交互或协议状态转换之前就执行的安全敏感代码。
规模：25 个开源项目、500 万行以上、语言含 C / C++ / Java / PHP / Python；Claude 建了 17,000 多个配置项的清单，其中 3,842 个与安全控制或安全特性相关；最终报出 493 个问题。
最有价值的发现是「配置组合」这一类：162 组安全敏感的选项组合被软件静默接受——不报错、不告警、也没有任何文档说明交互后的预期行为；其中 94 组直接把某个安全控制关掉；剩下 68 组是同一机制内部的不一致，例如配置说已禁用但监听或登录路径仍可达，或两个设置的优先级取决于它们在配置文件里的顺序。
反直觉的是 Gated 组（11 个「本该只服务已认证用户」的项目）结果最糟：93 处不必要的鉴权前暴露面、37 处在鉴权前执行代码或记录状态、61 组静默削弱鉴权前控制的配置组合。
两个案例值得抄进排查清单。一是 fail-open 的反向 DNS：四个互不相关的项目都出现同一模式——管理员用主机名或通配符写拒绝规则，但反向 DNS 查询默认关闭，服务器手里只有 IP，主机名规则永远匹配不上 IP，拒绝规则永不触发，名单 fail-open；部分项目文档提到主机名规则依赖 DNS 解析开启，但没有一个说明「这么写会放行」。二是证书校验冲突：一个本意「延迟校验」的选项实际把校验整个关掉，于是配置成「只接受可信客户端」的服务器会接受任何人的连接——这对冲突在软件里存在了 21 年。
OpenSSH 是最具体的修复样本：10.4 里约 4,500 行 ML-DSA-44（后量子签名）实验代码在默认配置下可被未认证客户端触达，即使管理员明确排除了该算法——因为守护进程先按客户端发来的 key type 解析（证书还要先验内嵌的 CA 签名），然后才检查该类型是否被允许。这 4,500 行约占默认 sshd 鉴权前代码的 16%。10.5 把检查提到解析之前；随后又发现两个缺口（检查看的是客户端声明的算法名，而解析器由 key blob 里的 type 字符串决定，于是可以声明 ssh-ed25519 过检、实际发 ML-DSA key），10.6 把检查放进解析器内部。默认构建下未认证可达的代码减少了约五分之一，而没有先找到任何一个具体漏洞。
这条路径的商业含义：它不减少未知漏洞的数量，但降低未知漏洞的严重性——对手里一堆没人看过的代码，这是唯一能规模化做的事。
