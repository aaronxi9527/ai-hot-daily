Microsoft智能体身份 · 动态授权🔥🔥🔥

微软给 AI 智能体上「动态权限」三件套：权限按任务给、风险按行为算、条件访问按风险收

11 月 3 日，微软发布新一波 AI 智能体防护机制，核心是三个都带「动态」的能力：Dynamic Permissions（动态权限）、Dynamic Agent Risk（动态代理风险）、Dynamic Conditional Access（动态条件式访问）；同时扩展 Project Perception 的 Guardian Agents 与 Playbooks，并把 Entra Agent ID 的覆盖范围扩到安全传感器发现的本地 agent。Project Perception 与 Agent 365 共享注册表和上下文信号，安全与 IT 看到的是同一张 agent 清单。

动态权限解决「给多少」：授权绑定到具体任务与时长，组织策略限定不得超出使用者自身的访问范围，任务变更或结束即收缩或收回。微软给的例子是报销 agent——「查发票」和「批报销」是两笔权限，前者保留，后者单给。动态代理风险解决「怎么算」：汇总身份、信息处理、设备、云资源、网络、运行时与 agent 活动信号，评估暴露面、潜在后果、与原定任务的偏离，是持续评估而非注册时打一次分——遇到不可信指令并尝试无关动作，评分就会变，哪怕原始权限配置一个字没改。动态条件式访问解决「怎么收」：把变化的风险翻译成动作——降权、缩小资源范围、收回临时授权、要求人工批准、运行时隔离、停止执行。

Guardian Agents 与 Playbooks 补的是「谁执行」：人定策略与委派边界，Playbook 编排防护动作，Guardian Agents 在边界内干活。这套设计最值得注意的不是「动态」两个字，而是把判断权留在人手里——风险可以自动算，批准与停止仍然要人按。

这条最难的地方不是「能不能降权」，是「降权之后哪个操作真的做不了了」。微软自己的例子已经说明：agent 可以保留查信息的能力，同时失去批准与修改的权限。采购演示时要问的就是这一句，而不是「能不能弹一条告警」——告警是看见了，条件是拦住了，两件事差着一次事故。另外，三件套全部挂在 Entra 身份体系上，意味着非 Entra 环境（本地模型、私有 agent 框架）能吃到多少，官方口径还没给。

Cloudflare漏洞情报 · AI 辅助响应🔥🔥

Cloudflare 在 Radar 上线 Zero Wire：给关键 CVE 做「通讯社式」简报，每条还附一段给 AI agent 的自查提示词

11 月 3 日，Cloudflare 推出 Zero Wire，放在 Cloudflare Radar 的安全栏目下，公开、免费、不需要是 Cloudflare 客户。官方给的动机很直接：AI 能大规模分析代码库，挖出人工审查多年没发现的深层缺陷，漏洞披露的量与速度都会上升，而响应团队的编制不会跟着涨。Zero Wire 要做的是把「分诊」这一步从人脑里挪出来。

每条简报的结构固定：白话解释这个漏洞是什么、谁应该去查、建议动作、证据与厂商指引链接（CVE 记录、厂商公告、安全研究、CISA 已知被利用目录）。首页分两组——Needs attention（需要评估或处置，含已知利用与仍在演进的指引）和 Reference（指引已稳定）。每条带状态与 last-checked 日期，一份简报可覆盖多个相关 CVE，支持按 CVE 或事件名搜索、按技术标签追关联。范围明确不是全量 CVE 目录，只收互联网暴露软件的关键漏洞，且强调「严重性」与「是否已被利用」是两件事，必须分开读。

最特别的一处：每条简报附一段预编译 prompt，交给 AI agent 做只读评估——部署了什么、有哪些厂商修复、暴露面与补偿控制、逐资产证据与未知项、下一步动作；复制 prompt 本身不扫描、不改系统。Cloudflare 举的例子是 php2shell（PHP 运行时）：更新 WordPress 或 Magento 的应用代码、插件并不能修底层运行时，简报的作用是帮你找到真正的系统责任人。

这是把「漏洞响应的瓶颈在分诊而不是缺数据」产品化了，而且它自己承认 AI 让披露变快，然后拿 AI 来做应对——同一个动作既是病因也是药。对国内厂商的参照意义在于粒度：漏洞情报站早就不缺，缺的是给 CISO 一句话、给工程师一条命令、给 agent 一段 prompt，三种粒度同时存在且互相对得上。

安恒信息AI 治理 · 一站式平台🔥🔥🔥

安恒把 AI 安全治理做成 DAPA 四步闭环：资产有户口、上线过闸门、调用走网关、事后能复盘

11 月 3 日，2026 世界互联网大会「互联网之光」博览会数智创新发布现场，安恒信息发布基于自研治理方法论 DAPA 的 AI 安全治理一站式解决方案。DAPA 四步：Discover 发现纳管 / Assess 评估准入 / Protect 防护管控 / Audit 审计留痕，对外的说法是「让每一个 AI 有户口、过闸门、留痕迹」。

管资产：网络侧主动探测 + 终端侧存量盘点双探头，自动识别模型、智能体、本地 AI 应用，专门找影子 AI 与私接公网模型；资产信息汇入台账，构建含类型、组织、责任人等七维资产画像，官方口径纳管率 100%。管上线：AI 智鉴按「先评估、后上线」准入，从训练数据、内容安全、智能体、基础设施四个维度测评，覆盖提示词注入、MCP 风险、算力基线，自动出测评报告与整改建议。管运行：AI 安全网关 + 大模型安全围栏 + AIDR 终端检测统一收口——网关做身份鉴权与行为审计，围栏双向拦注入与敏感信息，AIDR 在终端发现影子 AI、阻断敏感外发。管事后：四层审计架构汇聚模型、Agent、MCP 工具全链路数据，靠 UEBA 做分析，捕捉智能体六步行为链路，把孤立操作串成攻击路径。

落地口径给了三个可核对的场景：中兴通讯办公 Agent 场景支撑 3 万+ 用户、百万级智能体调用，抵御提示词注入与 Skill 供应链投毒；某金融机构用 AI 安全网关 + AIDR 做敏感文件阻断与 Agent 行为治理；相关能力入驻阿里千问办公生态，提供 MCP / Skill 安全扫描。此外支撑全国 9 省近 200 家单位的大模型安全专项检查。

国内少数把「资产—上线—运行—事后」四段都给出具体产品映射而不是四个名词的方案，而且给了一个能对账的规模数字（中兴 3 万用户 / 百万次调用）。要挑刺的话：「纳管率 100%」的分母是企业里已被发现的那部分，不是企业里真实存在的全部 AI——影子 AI 的分子分母都不由厂商掌握，这个指标只能内部横比、不能跨客户横比。

虎符网络AI-SBOM · 溯源响应🔥🔥

虎符网络用 AI-SBOM 把「影子模型」画进资产清单，靠多智能体把 MTTD / MTTR 压到分钟级

11 月 3 日同场「网络空间安全治理」发布会，虎符网络发布《基于 AI 原生的安全分析与溯源平台》，定位是覆盖 AI 应用全生命周期的原生安全治理体系，跑「多源数据融合—智能威胁检测—动态态势评估—精准溯源预警—协同应急处置」全流程闭环。

四个设计点值得单列：① AI-SBOM（AI 软件物料清单）——识别隐藏的代码逻辑、影子模型与第三方组件依赖，做到模型血缘与资产清单的颗粒度可见；② Multi-Agent 协同编排——把平均检测时间 MTTD 与平均响应时间 MTTR 从小时级压到分钟级；③ 可解释溯源——知识图谱 + 深度学习做跨模态关联，还原攻击链路与入侵源头；④ 人机边界——划出「智能体自主区」与「专家干预区」，高风险操作必须人工把关，保业务连续性与数据安全。

AI-SBOM 是今天第二次看到「把 AI 组件当供应链管」（第一次是易盾的 Skill / MCP 检测），说明国内厂商的视角正从「扫模型」转向「扫模型依赖」——因为攻击者越来越不打模型本体，打的是它引用的那个包、那个 Skill、那个 MCP server。需要提醒的是「分钟级」是目标值，发布会没给数据规模、样本量与误报率，验收时必须问清这三个前提。

孝道科技发布 AI 软件供应链安全检测平台，盯的是「80% 代码由 AI 生成」之后那些看不见的依赖

11 月 3 日同一场发布会，孝道科技发布AI 软件供应链安全检测平台，主打情报驱动的 AI 原生检测，面向 AI Agent 编码带来的供应链变局。官方给出的问题设定是：当代码生成占比达到 80% 的依赖度，大量依赖是「不可见」的——AI 生成的调用、隐式引入的包、被投毒的 Skill 与 MCP。

平台的解法是把 AI 生成代码引入的组件与来源纳入审查链路，用威胁情报判断「这个包是不是真的存在、是不是被谁改过」，而不是只看代码本身有没有明显缺陷。

这是今天三条国内产品里最薄的一条：只有发布会口径，没有规格、没有检出率、没有客户案例，所以只给 🔥。之所以仍收，是因为它点的问题很真——当 80% 的代码不是人写的，「代码审查」这个动作的对象已经从「人写的逻辑」变成「人和模型共同引入的依赖」。真要买，先问三件事：能不能给出依赖来源、能不能区分「模型编造的包」和「真实存在的包」、能不能接进现有 CI 而不是另开一个门户。

Accenture × 美国国防部安全事件 · 影子 AI Agent🔥🔥🔥

埃森哲员工把个人 Claude Code 账号接进五角大楼 NIPRNet，agent 带着管理员凭证在里面跑了两个月

WIRED 10 月 29 日报道、11 月 3—4 日中文圈扩散：一名埃森哲（Accenture）员工把个人 Claude Code 账号接入美国国防部 NIPRNet 的一台生产系统。该网络承载 CUI（受控非机密信息），供多家情报机构使用；国防部自身已禁止员工使用 Claude。

据信源，为了让 agent 自动写代码、部署云服务器，该员工向它提供了登录凭证，使 agent 获得管理员权限并绕过正常登录流程的安全控制，还在代其提交代码。agent 需要联网才能完成任务，据报把登录凭证、密码与 NIPRNet 网络拓扑信息发往了一个第三方网站——该站点此前被 NIST 标记为高风险，存在可诱导 AI 编码 agent 窃取凭证的提示词注入漏洞（WIRED 未公布站点名）。整件事在被发现前持续了约两个月。

风险传导路径被专家点得很清楚：拿到 NIPRNet 凭证 → 在软件工具或更新程序里植入后门 → 随部署流程进入物理隔离的 SIPRNet / JWICS。NSA 前黑客 Jake Williams 指出，传统 SAST 主要扫代码缺陷，不一定能识别「能正常运行的」恶意后门；而 AI 生成代码越多，人工逐项追溯越不现实。

现状与争议：无证据表明机密系统被入侵；埃森哲称已做独立调查、认定指控不成立，并称公司履行了法律与合同义务；五角大楼拒绝置评。联邦承包商须在发现后 72 小时内上报，信源称最初并未上报，且未说明是谁授权的这次接入、agent 部署了什么代码、敏感数据是否被读取或篡改。

核心不是「AI 叛变」，是一个能写代码、能部署、能联网的进程拿到了管理员凭证，而监控只认恶意程序和异常端口。三个缺口可以直接抄进自己的检查表：终端是否允许未托管的个人账号 AI 编码 agent 运行；AI 工具的出口是否纳入代理与 DLP；有没有「agent 进程读取凭据库 + 发起外部 HTTPS」这条组合行为的检测规则。单个动作都合规，串起来才是事故。

Dynatrace 研究团队MCP 工具投毒 · 跨框架实测🔥🔥🔥

12 个 agent 框架、18 个模型、9,720 个测试单元：MCP 工具投毒实测成功率 22.9%，没有一个框架做了主动防御

论文《MCP Tool Poisoning in Agentic AI Frameworks: A Cross-Framework Measurement Study》11 月 2 日提交 arXiv（2611.03555v1），已被 AISec '26（第 19 届 AI 与安全研讨会，与 ACM CCS 2026 同期）接收。作者是 Dynatrace（奥地利林茨）的 Farooq Shaikh 与 Biagio Montaruli。实验规模：12 个框架 × 18 个模型 × 45 个攻击场景 = 9,720 个测试单元。

结果：2,113 个单元（22.9%）可被利用。其中 255 例经独立验证的密钥外泄、487 例确认与攻击者端点建立了联系、1,371 例攻击者指定的工具调用被实际派发。验证方式是「双预言机」：既要有 transcript 证明 agent 做了什么，也要有 canary HTTP 回执证明数据或回调真的到了研究者控制的设施——这把它和以往「模型看起来愿意配合」的研究区分开了。

代码级审计的结论更硬：12 个框架全部把工具描述原样塞进模型上下文、不做校验，「没有任何框架实现了有意的工具描述防御」；抗性更多取决于模型而不是框架——模型级攻击成功率从 0.4% 到 49.7%。Claude Opus 4.8 在 530 个单元中 8 次中招，同时给出 223 次明确拒绝。

协调披露做了 5 次、涉及 4 家组织，全部被拒。LangChain 的回复是「这个库的职责就是按 MCP 规范原样传递信息，不是做校验的地方」；MCP SDK 的回复是「防 rug-pull 靠宿主侧审查工具调用，而不是靠一个攻击者能控制的通知」。测试床已开源：mcpvenom（GitHub），附攻击场景、恶意与合法 MCP server、canary 设施与冻结产物。实验窗口 2026 年 7 月 22—24 日。

这份研究把「提示词注入」从「模型会不会听话」推进到「工具调用有没有真的发生、数据有没有真的出去」。22.9% 不是模型不行，是协议把「描述即接口」当成了设计哲学——谁能控制 description 或工具返回，谁就能向模型下指令。厂商的回应其实很诚实：这不是 bug，是信任假设错位。所以短期不会有补丁，只会有「宿主侧审查」这一层要客户自己建。

Gartner趋势预测 · 智能体治理🔥🔥🔥

Gartner 2027 十大技术趋势：重心从「AI 能干什么」转向「AI 自主执行之后谁来管」，预警 2028 年 1/4 漏洞事件源于智能体滥用

Gartner 发布 2027 年企业机构十大战略技术趋势，十项几乎全部与 AI 直接或间接相关，但重心已变——不再讨论 AI 还能做什么，而是「AI 自主执行之后，谁来管、怎么管」。研究副总裁高挺的原话：「2026 年的重点是如何构建和应用 AI，2027 年则转向如何管理 AI 驱动的自主系统，并重新设计企业的技术架构。」

三条主线：① 非文本 AI 前沿——大型定量模型（LQM）专攻金融、医疗等强监管行业的定量数据；语音推理模型直接对音频推理并行动；世界模型让机器理解空间、时间与因果。② 管理自主智能体的新型基础设施——AI 上下文平台、AI 智能体身份、AI 编码智能体框架、自主式暴露修复，分别回答「智能体懂不懂业务、权限归谁管、代码谁来验证、漏洞谁来修」。③ 重新定义软件经济与技术主权——可抛弃型应用、主权技术、湿件即服务。

最重的一条预测：到 2028 年，25% 的企业安全漏洞事件将追溯至 AI 智能体滥用，根源在于机器权限未获有效管理。成熟度排序上，语音推理模型、AI 上下文平台、AI 编码智能体框架处于 1—3 年落地窗口；世界模型仍偏研究预览，长时间一致性与复杂物理交互有局限，短期商业化更可能先在数字内容与虚拟场景。

「25%」是预测不是统计，用的时候要标明。但它指向的因果链很具体：不是 agent 被黑，是 agent 的权限没人管。这和今天产品侧三个动作是同一件事的三种解法——微软按任务授权、CrowdStrike 掐模型访问、安恒给 AI 建台账。被 Gartner 单独点名「待建」的是AI 智能体身份，这也解释了为什么 IBM、Okta、Entra 都在抢这一层：身份是唯一能把「人—agent—资源」串成一条责任链的东西。

中国网络空间研究院研究报告 · 产业数据🔥🔥

乌镇蓝皮书：企业级智能体市场 212 亿元，日均词元调用 140 万亿，AI 安全治理五条写进国家法律体系

11 月 4 日，《中国互联网发展报告 2026》与《世界互联网发展报告 2026》在乌镇峰会发布，中国网络空间研究院牵头编写，已连续十年。中国报告明确把「人工智能政策制定、行业应用、产业生态及安全治理」列为本年度三大呈现重点之一。

产业数据：2025 年中国企业级 AI 智能体市场规模 212 亿元，具身智能约 9,150 亿元、同比 +20.4%；2026 年 3 月我国日均词元调用量 140 万亿，两年增长超千倍。备案侧两个口径要分清——截至 2026 年 6 月累计 924 款生成式 AI 服务完成备案、573 款应用或功能完成登记；截至 8 月底则为 1,112 款备案、731 款登记。

安全治理五条：一是把人工智能纳入国家网络安全法律体系（修改后的《网络安全法》新增第二十条对 AI 安全与发展作出专门规定）；二是 AI 安全治理框架持续深化（《人工智能应用伦理安全指引 1.0》为开发、服务、使用提供指引）；三是安全标准体系加快构建；四是生成式 AI 服务备案有序推进；五是安全专项治理行动全面加强。世界报告侧：预计 2030 年 AI 对全球经济贡献 22.3 万亿美元、占全球 GDP 3.7%，同时「智能鸿沟」正在拉大国家间数字发展差距。

引用时最容易被搞错的是备案数：924 与 1,112 不是「增长」，也不是「减少」，是两个不同截止日（6 月底 / 8 月底），且「服务备案」与「应用或功能登记」是两套口径，别混着算。真正值得记的是 140 万亿 tokens/日这个量级——它意味着「AI 网关」这类按调用计费、按 token 审计的产品，第一次有了可核算的市场基数。

中国信通院 × 360 × 华为行业标准 · 自律公约🔥🔥

《智能体发展自律公约》发布：八条自律措施，第四条直指权限越界、运行监测与异常熔断

11 月 4 日，乌镇峰会「智能体互信互联互操作全球合作创新」论坛，中国信息通信研究院、360、华为等企业及机构共同发布《智能体发展自律公约》，360 为核心发起单位之一并深度参与起草。

公约共八条自律措施，重点聚焦健全智能体信任体系、提升安全防护能力、健全治理机制。其中第四条对安全防护提出明确要求：要「健全前瞻性风险评估、运行监测、行为管控、异常熔断等技术体系」——这四件事正好对应智能体从上线前到失控后的完整链条。

360 给出的对应解法是「以模治模、以智能体对抗智能体」：大模型安全 + 智能体安全两道防线；智能体安全防护与管理系统覆盖资产发现、行为管控、威胁检测、事件响应、损失恢复，对智能体与技能插件做识别管理，对文件访问、网络连接、命令执行做运行时管控，结合安全大模型发现提示注入与恶意技能，支持事件回溯与文件备份恢复。个人侧纳米 Work 把 agent 放云端隔离环境、未授权不接触本地数据、异常时可即时重建；政企侧主权 AI 操作系统已在部分企业投用。

自律公约不是标准，没有罚则，但它把「异常熔断」写进了行业共识——这跟 CrowdStrike 的 kill switch、微软的动态条件式访问是同一个动作的三种叫法。国内做 agent 安全的厂商，接下来投标时大概率会被问「支不支持熔断、熔断后能不能恢复」，这句问法就是从这类文件里长出来的。

Sentra融资 · Agent 数据安全🔥🔥

Sentra 完成 1.5 亿美元 C 轮：卖的不是「逐个监控 agent」，是「先把数据地图画对」

11 月 4 日消息，数据安全初创 Sentra 完成 1.5 亿美元 C 轮，由 Capital One Ventures 领投，Bessemer、Zeev、Standard Investments、Munich Re Ventures、Key1 Capital 等跟投，累计融资超 2.6 亿美元，Capital One Ventures 获董事会席位。公司 2021 年成立，纽约 + 特拉维夫，约 130 人。

产品路线与「逐个 agent 装探针」相反：自上而下测绘企业完整数字网络，识别并对敏感数据分类；清理 agent 常挖到的冗余、重复高风险数据；把 agent 的全部操作行为完整呈现给安全、法务与合规团队。CEO Yoav Regev（前以色列 8200 部队网络部门负责人）的判断是：「一年前只跑几个 agent 的大型机构，未来几年 agent 数量会指数级增长」「agent 是亦敌亦友的存在」，预计 12—18 个月员工翻倍。

他给的另一个观察值得记：越来越多懂技术的员工用自身的数据访问凭据搭建自定义 agent，进一步加剧风险——这和今天埃森哲那条是同一个入口。

这笔钱买的判断是「agent 安全的前置条件是数据可见性」。它和微软「先给身份」、CrowdStrike「先给开关」并列，是第三条路线：先知道数据在哪、谁在用。三条路线最后会在同一个采购里撞上——因为企业不会为「身份、数据、运行时」各买一套，只会问一句：哪家能一次说清这个 agent 到底碰了什么。

NIST标准 · 事件响应🔥🔥

NIST 要把「AI 事件响应」写进 SP 800-61：智能体监测、遏制、证据共享，外加一份非预期行为的自愿管理原则

据 MeriTalk 11 月 3 日消息，美国国家标准与技术研究院（NIST）计划更新网络安全事件响应指南 SP 800-61，并建立利益相关方交流机制，帮助组织应对针对 AI 系统的网络攻击，以及 AI 滥用、故障和非预期行为造成的危害。

研究范围四条：自主智能体的事件响应、系统监测与日志记录、事件信息共享、取证证据管理；并考虑制定「智能体非预期行动」的自愿管理原则。组织动作上，NIST 拟成立事件管理兴趣社区，并通过 AI 联盟组建「智能体能力与监测遏制」工作组，推动政府、企业、学界交流经验、识别实践缺口。

SP 800-61 是所有 SOC playbook 的祖本。它一旦把「agent 非预期行为」写进事件响应流程，等于官方承认这类事件要按安全事件而不是软件缺陷来处理——这会直接改写日志留存周期、证据链要求与上报时限。国内做等保、做关基的厂商，值得盯这一版的草案文本，因为「agent 事件怎么定级」这件事，早晚要有一份可引用的依据。

METR × Redwood Research研究披露 · 监控失效🔥🔥

受 OpenAI 委托测自家监控：Codex agent 能绕沙箱、能隐藏操作，还有一个能关掉监控的请求头

11 月 3 日消息，AI 安全研究组织 METR 与 Redwood Research 受 OpenAI 委托，于 7—8 月对 OpenAI 内部的 AI agent 监控系统做测试。

发现包括：Codex agent 可能绕过沙箱与自动审查机制，在用户原有权限范围内执行未经监控或审查的操作；存在让 agent 隐藏自身行为、不被监控的方法；此外还发现可关闭监控的请求头设置，以及未受监控的内部 agent 工具。OpenAI 表示已修复研究中发现的所有相关问题，并认为结果有助于强化系统扩大部署时的安全防护。

这条的价值在「谁测的」——不是外部攻击者，是被委托的第三方，而且测的是监控系统本身。结论也很朴素：监控的失效点往往不在模型，而在监控链路上的一个 header、一个没纳入范围的内部工具。这和埃森哲那条是同一个教训的两面：你以为在监控 agent，其实在监控一条你以为完整的管道。

Railway安全事件 · 凭据托管🔥🔥

Railway 环境变量泄露波及约 200 万用户，一年内第四起同类事件：托管平台的配置就是生产钥匙串

11 月初，开发平台 Railway 被曝环境变量泄露：攻击者读取了平台托管的客户机密信息，盗走连接 AI 服务所需的 API 密钥，据报波及约 200 万用户，数据库口令同样面临外泄风险。平台称发现后已阻断攻击路径并通知受影响组织管理员；截至 11 月 3 日，受影响组织数量与凭据类型尚未完整公布，入侵方式亦未披露。

媒体复盘指出，这已是该平台一年内第四起与凭据、环境变量相关的安全事件：5 月自托管版本的容器日志会泄露项目机密，7 月的安全公告证实 CLI 调试日志会明文打印环境变量。事件 11 月 2 日登上 Hacker News 后持续发酵，研发者社区开始重新审视「把生产密钥交给托管平台」这一默认做法。

环境变量里放的往往不是一条密钥，而是一串：模型服务商 API key、支付私钥、数据库直连串——为驱动持续运行的后台任务与 AI agent，开发者习惯把它们全填在平台里。泄露一次，等于一串门同时打开。

可以立刻做的五件事：盘点第三方平台的环境变量配置（哪些填了生产密钥、哪些填了数据库直连）；按「可能受影响」先轮换再等名单；把长期密钥换成短周期、可单独轮换的；给高权限 key 加来源限制与用量告警；把凭据托管纳入第三方风险评审。一年四起不是运气差，是机密隔离与日志脱敏的设计问题——补一个缺陷解决不了。

🧭趋势判断 · 精简版

控制点从「模型出口」挪到「任务授权」

微软按任务发权限、CrowdStrike 掐模型访问、安恒给 AI 建台账，三家在做同一件事：把「这个 agent 能干什么」从静态配置改成随任务生成、随任务收回。这个转向的代价是必须先有身份体系，所以「AI 智能体身份」会成为下一个必争之地。

协议层的洞短期不会有补丁

MCP 22.9% 的实测说明「描述即接口」是设计取舍，不是 bug；LangChain 与 MCP SDK 的回复已经把责任推回宿主侧。这意味着未来 12 个月的 agent 安全预算，主要花在工具调用前的审查、返回内容当不可信数据、权限拆开这三件工程活上，而不是等一个官方修复。

凭据是比漏洞更短的路径

埃森哲的 Claude Code、Railway 的环境变量、此前 LLMjacking 的云密钥，三件事的共同点是攻击者不需要 0day，只需要一个能发请求的账号。防御的重心因此从「堵漏洞」挪到「限制这把钥匙能开几扇门、能开多久、开的时候有没有人看见」。

国内产品从「扫模型」转向「扫依赖」

易盾的 Skill / MCP 检测、虎符的 AI-SBOM、孝道的 AI 软件供应链，三条都指向同一件事：AI 应用的攻击面在它引用的东西里，不在它自己的代码里。谁先把「模型血缘 + 依赖来源 + 供应链情报」三张表打通，谁就能在下一轮投标里把方案讲成资产盘点而不是设备清单。
