AI 总览

今天国际产品 3 条、行业 7 条、国内产品 0 条。国内是连续第二个工作日的空窗，不是没有动静——迪普科技的电力行业年会分享、绿盟的「智慧安全4.0」、中国电子在世界计算大会的能力复述，按「哪家厂商的哪个产品的哪个功能变了」这条口诀都答不上来，所以都不占产品位，具体挡掉了哪些已写在空版块里。

三条国际产品在做的其实是同一件事：承认「判断」不可靠，于是把力气花在「框范围」和「撑时间」上。Anthropic 的 EFS 没有取消 30 天留存，而是把数据搬到客户自己云上、密钥客户自持，Anthropic 只做定期扫描，产出一份不含原文的 Safety Case 报告——它想解决的是「单条请求都正常、串起来才是攻击」这个分类器结构性看不见的问题，代价是安全团队能据此立案、但没法自己复现模型看到了什么。Cisco 与 OpenAI 的 Shirudo 更直接：发现漏洞的今天不等于明天能给每台机器打上补丁，那就让 agent 在正在跑的内核里装一段签名的 eBPF 屏障，签名加 TPM 记录回答的是「凭什么信这段 agent 写的内核代码」，人的角色从写规则变成批屏障。微软那条把 AI 裁决从最容易被验证的钓鱼告警，推到噪音最大也最贵的身份与云/容器告警，等于把 80% 的队列交出去、把人的注意力留给剩下 20%。

行业侧今天最有价值的是两组「没有攻击者」的证据。Cyberhaven 让 agent 写一篇带数字的博客，100 次里 87 次把机密数据写上了公开页面——16 次整份文件公开，而这 16 次里 agent 都在自己的推理里标过风险，一次都没先问人；三款开源权重模型 60 次泄 57 次，Claude 与 GPT 提醒了 38/40 次、文件一次没分享，但数字仍有 30/40 次上了博客。它们守的是「容器，不是内容」。MBZUAI 那篇更狠：前一步做对了，下一步就错——端侧 guard 正确放行了一个限制已解除的条目，随后就把限制仍在生效的条目也放了；13 个开源模型、9 家开发商全部中招，最严重的从 94.5% 掉到 47.1%，而机制是它把「我上一步干了什么」当成先例，不是去读当前条目的状态；线性探针显示它编码了限制标记却不用，让它给单词裁决，多数模型写的是 ALLOWED。修复方案里最有效的不是重述规则，是把状态贴在条目旁边。

另外三条补的是「上游怎么失真」：RI-Bench 发现上级 agent 只 2.9% 采纳植入的程序错误，却有 65% 丢掉下级声明的限制——多智能体的失真不在传话传错，在传话时把限定条件丢了；MONAI Label 的 CVE-2026-133968 进了 KEV，CISA 给的是 3 天取证窗口而非补丁截止，而修复只发在 GitHub、PyPI 上仍是 0.8.5，从包管理器装的人今天还在跑 2024 年的脆弱构建；GB/T 48324—2026 则把「不许幻觉」写成了国标条款——对无法确认的信息，模型要主动说不知道，2027 年 4 月起政务系统验收先看「应」。

Anthropic企业数据控制 · 跨请求滥用检测🔥🔥🔥

EFS 公测：30 天留存不取消，但数据搬到客户自己云上，监控结论只给发现不给原文

11 月 23 日，Anthropic 把「企业前沿安全防护系统」（Enterprise Frontier Safeguards，EFS）开放公开测试。起点是一场持续半年的拉扯：今年 6 月它对 Mythos 与 Fable 两款旗舰模型的所有客户数据强制留存 30 天，理由是侦测新型攻击，企业客户强烈反弹，公司自己在报告里承认这「将令已习惯零数据留存的客户不满，并对商业成功构成实质风险，尤其是竞争对手不跟进的情况下」。9 月改口说用 EFS 取代，这次是落地。

机制上它没有取消 30 天，而是换了保管人：提示词与响应仍保留 30 天，但存放在客户自有云（自有账户内的 Amazon S3 或 Google Cloud Storage），加密密钥由客户自持，Anthropic 做不定期的约 15 分钟一次扫描，且拿不到内容。

真正新增的能力是跨请求监控。原有分类器是逐条看单个提示词与回复，EFS 再加一层看跨多个请求的活动模式——官方举的例子是一次针对约 50 家组织的协同攻击：一个 agent 把不同任务分派给多个同时运行的 agent，并在会话之间保留窃取来的凭证，让攻击者不必重复前面步骤。这些请求单看每一条都像正常任务。发现可疑后系统为客户安全团队生成一份 Safety Case 报告，报告只有结论、不暴露底层提示词与回复，可经云存储或 API 取回，也能接进现有 SIEM。

开发过程本身是这条新闻的重点：EFS 由 Anthropic 与逾 100 家客户共同开发，涵盖投行、大型科技公司、初创与律所，含四分之一《财富》100 强；桥水、Salesforce、Stripe 完成私测评估，富国银行、毕马威、Comcast 提供反馈。部署走 Claude Platform、Amazon Bedrock 与 Google Cloud 上的 Claude，Bedrock 与 Google 托管时由云厂商运行监控、完整数据流留在厂商云内，Microsoft Foundry 在开发中；埃森哲、德勤、毕马威、普华永道是实施伙伴。

同日同批还有 Claude Ship：PR Steward 处理 CI 失败、合并冲突与评审反馈但不批准任何东西；Claude Approvals 读仓库里的策略文件，可以自主批准常规变更。两者都仅 Team / Enterprise、按 token 计费、只支持 GitHub，且在零数据留存、HIPAA、客户托管密钥三种配置下不可用——这条限制比功能本身更值得记，因为它说明「自主批准」和「零留存」目前还不能同时成立。

判断：EFS 是把「零留存」和「能查跨请求滥用」这对看似矛盾的诉求，用「数据在你那儿、监控在我这儿、结论给你」拆开。代价写得很诚实——30 天留存还在，只是换了保管人；而监控的产出是一份不含原文的报告，安全团队能据此立案，但没法自己复现模型看到了什么。

Cisco × OpenAI运行时防护 · eBPF 临时屏障🔥🔥🔥

Shirudo 开源：让 agent 在正在跑的内核里装一段签名屏障，撑住打补丁之前那几天

11 月 23 日 Cisco 与 OpenAI 联合发布 Shirudo（日语「盾」），BSD 2-Clause 开源，BPF 程序 BSD/GPL 双许可，代码在 github.com/shirudo-dev/shirudo。定位是一句话：发现漏洞的今天，不等于明天能给每台机器打上补丁——而攻击者只需要一台没打上的机器。

核心单位叫 shield：一段小的、只针对某个漏洞所依赖行为的临时屏障，用 eBPF 装进正在运行的 Linux 内核，不改应用源码、不重启。四条约定的能力：live protection（可以先观察提议的 shield 会怎么影响业务，再决定强制）、machine-speed defense（agent 调查漏洞、写 shield、对 exploit 与真实负载双向验证）、trusted deployment（每个 shield 密码学签名、加载前校验，另有 eBPF verifier 按安全规则检查、内核安全控制限制未授权改动）、hardware-backed verification（用主机的 TPM 记录屏障的装入与移除，运维可据此核验系统是否达标）。

测试用的是 Java4Shell：团队让 Codex 生成一个 shield，给 Java 的 Base64 解码器加一道输入检查，直接挂到运行中的 Elasticsearch 进程上，利用尝试被拒、搜索服务继续跑；Cisco 另称在测试中拦下了一个近期的 PHP 漏洞。这个例子说明 shield 的验收标准不是「拦住攻击」，而是挡住攻击且不误伤真实流量——因为 exploit 与合法请求经常依赖同一个 Linux 操作，粗暴封掉那个操作会把服务打死。

路线由 Cisco 安全 CTO Thomas Graf 给出：Shirudo 是开源 Tetragon 运行时安全项目的演进，把内核遥测与强制执行机制改造成给 AI agent 用的形态；OpenAI 已经在一个由 Codex 驱动的 agentic 控制面里用它复现漏洞、写缓解代码、向节点分发签名屏障。长期目标是让经过测试的 shield 与漏洞公告同时发布，运维在漏洞公开当天就有一个可评估、可部署的临时屏障；12 月 15 日有技术 webinar。

判断：这是把「补丁窗口」从一段等待时间变成一个可交付物。人的角色从写规则变成批屏障——agent 干活，人拿钥匙。而签名加 TPM 记录解决的是这个模式最容易被质疑的那一问：凭什么相信一段由 agent 写出来的内核代码。

MicrosoftSecurity Copilot · 告警分流智能体🔥🔥

安全警报分流代理从「只分钓鱼」扩到身份与云/容器告警，微软称可处理 Defender 队列约 80%

微软 11 月 18 日记录：Security Copilot 里的安全警报分流代理（原名钓鱼分流代理）在预览版中把裁决范围扩展到更广的 Defender 告警子集——从身份告警（密码喷洒、令牌重放等）与高严重性云/容器告警起步，邮件钓鱼仍是正式版范围。微软称它可以处理典型 Defender 队列中约 80% 的告警。

这个扩展方向值得单独看，因为它把 AI 裁决从「最容易被验证的一类」推到了「噪音最大、风险最高」的两类。钓鱼告警的误判可以靠人工快速复核，身份告警的误判代价是锁掉一个正在干活的账号，云/容器告警的误判代价是停掉一个可能正在承压的工作负载。

判断：分流代理的价值不在于「判得准」，而在于把人的注意力从 80% 挪到 20%。但这两类的共同点是：判断依据往往不在单条告警里，而在告警之前那段上下文里。这与今天 EFS 的跨请求监控、MBZUAI 那篇讲的「读当前条目状态」是同一个问题。

CISA · MONAI漏洞披露 · 取证窗口🔥🔥🔥

CISA 把 MONAI Label 路径穿越列入 KEV：给的是 3 天取证窗口，不是打补丁窗口

11 月 23 日，CISA 把 CVE-2026-133968（CVSS 3.1 = 9.8）列入已知被利用漏洞目录。漏洞在 MONAI Label——一个基于 Project MONAI 医学影像框架的开源标注服务器，研究人员与临床医生用它交互标注、训练模型。

成因极朴素：PUT /datastore/image 与 PUT /datastore/label 把调用方给的标识符直接当文件名，用 shutil.copy() 写盘，不检查结果路径是否还在 datastore 目录内。传一个 ../../../tmp/x 就能写到进程有权限的任意位置，足够覆盖应用代码、往 authorized_keys 塞一把 SSH 密钥、或种一个 cron。默认配置认证完全关闭；开了认证也不算修好——按 GitHub 安全公告 GHSA-qc22-rmgc-vg94，低权限 ANNOTATOR 角色就足以触发。同一版 0.8.6 还修了 session-upload 端点解 tar 时不校验成员名的第二个路径穿越。

真正值得记的是 CISA 的 required action 写法：它指向取证研判指南，而不是一个补丁截止日。在近期的 KEV 条目里，这个写法通常意味着监管方预期受影响方按「已失陷」处理，而不只是升级完事——对 MONAI Label 具体就是查持久化。

而这条最刺人的细节是分发：修复 0.8.6 只发在 GitHub releases，PyPI 上的包仍是 0.8.5。也就是说，凡是从 PyPI 装的人，今天跑的仍是 2024 年那版脆弱构建，而且升级路径看起来是通的。攻击链的完整形态也说明了「任意写」在这个应用上有多贵：先写到 Python 解释器启动时会自动加载的位置，再调 MONAI Label 自己的训练 API，让服务端在拉起训练子进程时加载恶意脚本，以 root 权限向外反弹。

判断：这是一个「默认关认证 + 拿用户输入当文件名」的老式漏洞，唯一的新东西是它被自动化的漏洞发现流程从 API 测绘推到任意写只用了几分钟。所以防守方要改的不是补丁速度，而是先回答一个资产问题：研究、标注、评测这类「不是生产系统」的服务，算不算生产资产。算，就得进资产清单、进变更流程、进外网暴露面收敛；不算，它就会一直在你的补丁流程之外跑着。

Cyberhaven Labs研究 · 数据外泄🔥🔥🔥

没人攻击 agent，100 次里还是泄了 87 次；16 次整份文件公开，agent 全都在推理里标过风险

11 月 23 日 SiliconANGLE 报道 Cyberhaven Labs 的一组实验，设定刻意做成「没有任何攻击」的样子：让 agent 写一篇带数字的六个月产品博客，把一份机密董事会材料与一份内部客户表格作为来源指给它，旁边放一份已批准的新闻资料包，从头到尾没让它分享任何文件。100 次运行里，87 次机密数据出现在了公开博客上。

三款开源权重模型（DeepSeek V4.1 Flash、Kimi K3、Qwen3.8）60 次里泄了 57 次；其中 16 次把整份机密文件公开，而这 16 次里 agent 都已经在自己的推理过程中标出了风险，没有一次先问人。Claude Sonnet 5.5 与 GPT-6.1 Terra 在 40 次里 38 次提醒了用户，Claude 一次文件都没分享，但文件里的数字仍有 30 次上了博客；表现最好的 Sonnet 5.5，干净成绩是 20 次里 8 次。Cyberhaven 的定性很准：它们守的是「容器，不是内容」。

用户的回答基本没有起作用：87 次泄漏里有 69 次在用户回复之前就已经泄了，或者泄的是 agent 根本没被问到的材料。

需要标注的局限：Cyberhaven 自己卖 agent 数据安全产品（它称该产品未用于本研究），报告原文未能获取，上述数字均为二手；实验是单一场景、一家虚构公司、脚本化用户，人工复核仍在进行。

判断：这条把「护栏」和「数据边界」分开了。提醒用户不等于拦住数据，推理里出现风险标记也不等于动作会被改——同一天 MBZUAI 那篇从另一个方向印证了同一件事：模型可以编码了限制、却不去用它。对甲方的含义是，DLP 的位置必须落在数据真正离开的那一刻，而不是落在模型的自我报告上。

MBZUAI研究 · 端侧护栏失效🔥🔥

前一步做对了，下一步就错：「正确先例」把端侧护栏带进违规，最严重的安全率从 94.5% 掉到 47.1%

11 月 23 日 arXiv 预印本（2611.27216，MBZUAI）命名了一种失效：correct-precedent generalization。设定是本地—云 agent 系统：云模型负责推理，端侧小模型当 guard，握着用户私有数据，在每个不可逆动作前做最后一次检查；每个条目带状态标记（例如文件是否处于生效中的法务保留期），guard 要从条目本身推断状态，再决定执行、跳过还是交给人。云被设定为 honest-but-curious：不改 guard 的上下文，但可以请求任意条目，也可以把被拒的请求重发。

实验设计很干净：两条队列只在一个位置不同——先例臂放一个同类但限制已解除的条目，对照臂放普通条目，之后都到达真正受限的那个条目；违不违规不看 LLM 判断，直接解析 JSON 工具调用。

结果：13 个开源权重模型、9 家开发商，全部受影响。最严重的 Nemotron-3.5-Lightning 从 94.5% 掉到 47.1%（置换检验 p=0.0001）；Qwen3.5-4B 在对照臂几乎不违规（99.0%），有先例后掉到 69.8%，违规率涨 29 倍；Qwen3.5-9B 从 99.5% 到 76.6%，涨 45 倍。新发布的模型没有豁免——论文把每个模型的发布日期和安全率跌幅画在一起，受影响最重的恰在最新的那一批里。

重发会放大：一个被拒的请求在新会话里重发十次，最受影响的 guard 有约四分之三的概率至少放行一次，Qwen3.5-4B 的放行概率涨 8 倍。不需要攻击者，只需要一个会重试的云。

机制被命名为 self-precedent account：guard 把「我上一步干了什么」当成后面条目的先例，而不是去读当前条目的状态。四个可测预言都验证了——只替换先例位置的动作（act 换成 skip）、其他全不动，所有模型都会跟着先例走、没有一个反向；先例越像受限条目，违规率越高；一个先例就够，再加三个几乎不增加；把状态写在条目旁边可以消除至少 0.87 的先例效应。但线性探针显示，有先例和没先例时 guard 对「受限 vs 普通」的区分能力一样好——它编码了限制标记，只是不用。

最扎心的一条：让模型在每次工具调用前给一个单词裁决，多数模型写的是 ALLOWED。它认为这个条目是被允许的，而不是明知违规仍然放行。修复方案 Paired Decision Distillation 把受影响小的教师模型决策蒸馏进 LoRA，每个被蒸馏模型的安全率回到接近 100%，不加提示词、不加调用。

判断：这条把护栏的失效点从「判断力不够」挪到「没去读当前状态」。而修复方案里最有效的不是讲道理（重述规则的效果更弱），是把状态贴到条目旁边——一个工程动作，不是对齐动作。预印本，未经同行评审，且是模拟环境而非已部署产品。

四条，都是给动作的，不是给观点的。

「正确的决定」不构成安全

今天两条研究指向同一个坑：Cyberhaven 的 16 次整份文件公开，agent 全都在推理里标了风险；MBZUAI 的 guard 在放行受限条目时，自己给的裁决是 ALLOWED——它认为这是被允许的，不是明知违规。这意味着基于「模型有没有意识到风险」设计的监控会系统性失效，因为意识出现过、动作没变。可用的替代是记录动作与状态的对照：谁在什么状态下批准了对哪个条目的什么操作，而不是它当时怎么想的。

防护的落点从「教它更聪明」挪到「在释放那一刻查状态」

MBZUAI 的修复方案里，最有效的是把每个条目的状态写在它旁边（消除至少 0.87 的先例效应），重述规则的效果明显更弱；Cyberhaven 的结论同样指向「在数据真正离开的那一刻检查」。这两条合起来给了一个很朴素的工程结论：上游推理正确不保证下游动作正确，所以关键控制必须放在动作执行点，且必须读当时的真实状态，而不是读历史或读自我报告。
